# Handoff: `devel/morton_spread` atomic-free spread prototype

## Goal

Make the standalone atomic-free 3-D type-1 spread prototype (`atomic_free_spread.{cuh,cu}`) competitive with cuFINUFFT method 3 (`gpu_method=3`, `gpu_spreadinterponly=1`, Horner, ns=6, sigma=2) **without giving up its identity as a readable, independent correctness reference**: one thread owns a box of output cells, every cell written exactly once, no global atomics, no splits, no active-tile lists, host-side binning/sorting, bitwise-comparable output.

A second, explicit goal from review: keep the file readable — comments describe only the present code (no measurements, history, or alternatives); no support-placement arithmetic in the cell loop.

## Design Decisions

**Ownership / correctness contract**
- Output-cell-owned: a block owns one tile; a thread owns a `GROUP_X × GROUP_Y × GROUP_Z` box; each cell accumulates over the block's candidate points in bin order then point order, and is stored once at the end.
- No early returns while barriers remain: cells past a partial tile are excluded by a store predicate (`store_cell_group`), because the batch loop carries `__syncthreads()`.

**Staging (the readability device — do not dismantle)**
- Each block stages a batch of `STAGE_POINTS` candidate points into shared memory as **tile-local, zero-filled** vectors: `kx[j][local]`, `ky[j][local]` = weight of staged point `j` for cell `tile + local`; `kz[j][local]` = `float2` of that weight **already multiplied by the point strength**.
- Three staging lanes per point, one per dimension: `fold_rescale` → `ceilf` → one `eval_kernel_vec_horner` → `TILE_*` slots via `stage_tile_weights()`, which calls the existing `coefficient_index()`. Support placement / wrap / partial-tile logic lives **only** here.
- Consequence: the cell loop has no support test, no branch, no coefficient select, no magic offsets. This is why `exp_a_cartesian.cu`'s `place_support()` machinery was deliberately **not** imported.
- Zero weights add exact zeros; a non-finite point strength would now reach cells the point does not cover (documented in a comment).

**Numerics**
- Multiply association is `(kx*ky) * (kz*strength)`, preserved from the pre-group version, so the uniform case is **bitwise identical** (`relL2` 5.285e-07 → 5.286e-07).

**Layout / geometry**
- Staged rows padded to **odd** float stride (`TILE_X + 1`, etc.) so staging lanes writing the same `local` of 32 consecutive points hit distinct banks (removes 46.4 M store bank conflicts).
- Current: `TILE_* = 8/8/8`, `GROUP_* = 2/1/2`, `BLOCK_X/Y/Z = 4/8/4` = 128 threads, `STAGE_POINTS = 32`.
- Block shape is deliberate: a warp must stay on one `z` slice so `kz` reads stay a broadcast.
- Constraints encoded as `static_assert`s: tile divisible by group; `3 * STAGE_POINTS <= BLOCK_THREADS` (all three dimensions staged in one round); `STAGE_POINTS % 32 == 0` (each warp stages a single dimension, so the `stage_dim` branches never diverge).

**Extracted helpers** (post-review): `cell_weight()`, two `stage_tile_weights()` overloads (`float*` and `float2*` + strength), `accumulate_batch()`, `store_cell_group()`. All `__forceinline__`; codegen verified identical to the inlined form.

## Trade-offs

- **Per-bin batching, no cross-bin filling**: sparse bins hold ~3 points, so a batch is 3 points → barrier 25 % of warp state on sparse. Cross-bin chunk filling was deliberately deferred (it was the only deferred piece of the original "chunking" plan).

- **`GROUP` choice (2/1/2 vs 2/2/1)** was made to keep a warp on one `z`; a `2×2×2` group (0.75 loads/cell) needs 64-thread blocks, which breaks the warp-uniform staging rule.

- **Stage per-point kernel weights into shared memory, indexed by cell position inside the tile** (tile-local, zero-filled). - **Strength folded into the z row** as `float2` (`kz * strength`): 3 shared loads per cell instead of 4, and 3 FP ops instead of 4.

## Trade-offs

- **Batch size is boxed in** by `3·P ≤ BLOCK_THREADS` and `P % 32 == 0`. Both conditions are needed; violating either costs 26–37% on sparse. P=64 is the max for a 256-thread block, P=32 for 128.
- **Group size vs tile size**: `threads × cells_per_thread = tile cells`, so more cells per thread means a bigger tile, and candidate points per cell grow as `(L+6)³/L³`. Measured/derived: 8×8×4 C=1 → 11,700 visits/cell; 8×8×8 C=4 → 15,616; 8×8×16 C=4 → 23,424. Loads/cell = `(gx+gy+gz)/(gx·gy·gz)`.
- **Zero-fill does work for cells the point does not cover**: 216 M useful contributions vs 3.07 B cell-visits. It buys a branch-free, divergence-free loop (active threads/warp 23.9 → 31.1) and is cheap per visit now.
- **Precision/order**: the strength fold changed the multiply association (relL2 shifts within the method-3 reference's own noise); the group version restored association and is bitwise identical on uniform. The rejected ILP variant also changed summation order — another reason it was dropped.
- **Registers sit at 63** (64 is the ceiling for 1024 threads/SM). Any growth drops occupancy to 3 blocks.
- Comment/naming policy for this file: comments describe only the current code, no measured numbers or history; ≤90 columns, LLVM 2-space. The readability of the staging invariant is treated as a hard requirement, not a preference.

## Open Questions

- Do we go to **option D** (64-thread blocks, 2×2×2 groups)? It needs `P = 16`, which breaks warp-uniform dimensions, so staging would have to become dimension-agnostic — feasible because a cubic tile makes all staged extents equal, so the dimension only selects *data* (coordinate, `grid_size`, tile origin, destination row). Predicted ~1.3–1.5× on uniform. This is the one place the design could get unreadable; decide deliberately.
- Is **cross-bin batch filling** worth it for sparse (a 3-point bin cannot fill a batch, and `P` is fixed at 32)?
- **Double buffering** the staged batch (1 barrier instead of 2) — barrier is now 22.9% uniform.
- Is the **point-owned shared-atomic scatter** on the table at all? It removes the 238/256 wasted cells per point but makes results order-dependent, contradicting this file's deterministic contract.
- Is the untested `float4` packing of `(kz, strength)` (one `LDS.128` instead of two loads) worth a measurement? It was proposed, the user doubted it, and it remains unmeasured — the risk is that 128-bit shared loads issue in 8-lane phases and cost *more* wavefronts than the two broadcasts they replace.
- Should the staging body be extracted like the other two helpers (offered, not done — it needs 8 arguments).
